## 0. 배경과 핵심 결정

### 관찰: "학회 명찰 출력" 네이버 검색은 플랩패스 독점

네이버에서 "학회 명찰 출력"을 검색하면 플랩패스(경쟁사) 네이버 블로그 글만 나온다.
이것이 알려주는 사실:

1. **이 키워드군의 네이버 노출 지분은 네이버 블로그가 차지한다** — 웹문서(자체 블로그)로는 이 지면에 못 들어간다. beoksolution.com 글이 아무리 좋아도 네이버 통합검색의 블로그 탭/스마트블록에는 안 뜬다.
2. **경쟁 강도가 낮다** — 한 업체 블로그가 독점 중이라는 것은 제대로 쓰는 경쟁자가 사실상 하나뿐이라는 뜻. 같은 품질로 꾸준히 쌓으면 지분을 나눠 가질 수 있는 틈새다.
3. **플랩패스가 이기는 방식이 곧 교본이다** — 자사 네이버 블로그에 단일 주제(행사/명찰)로 꾸준히, 현장 사진과 실무 디테일을 넣어 발행. 이게 C-Rank(블로그 단위 주제 일관성·활동성) + D.I.A.+(문서 단위 경험·구체성) 알고리즘이 원하는 형태다.

### 핵심 결정 3가지

| 결정 | 근거 |
|---|---|
| **봇 발행 금지, 수기 발행** | 네이버 자동화는 계정 정지 리스크가 실재하고, 현재 `content_quality.publish_blockers()`도 naver 채널을 전면 차단 중("이미지 업로드 보존 미검증"). 봇 코드(executors/naver-blog-worker)는 유지하되 이 기능에선 쓰지 않는다. |
| **하루 1건 상한** | C-Rank는 활동 "꾸준함"을 보지 물량을 보지 않는다. 하루 여러 건은 오히려 스팸 신호. 매일 1건 × 90일이 목표 형태. |
| **기존 근거기반 엔진 재사용, 톤·구조만 별도** | 근거 수집→evidence pack→게이트 흐름은 그대로 쓴다. 다른 것은 (a) 문체(수기 블로그 톤), (b) 출력물(붙여넣기용 HTML), (c) 종착 상태(발행이 아니라 "수기 대기"). |

## 1. 무엇이 "네이버에서 사람이 쓴 좋은 글"인가 — D.I.A.+ 신호 명세

기존 selfhosted 원고(정보 밀도 중심, 개조식)와 반대 방향의 요구가 많다. 프롬프트·게이트를 공유하면 안 되는 이유다.

### 1.1 네이버가 우대하는 신호 (프롬프트에 반영할 것)

| 신호 | 구체 형태 | 기존 selfhosted 원고와의 차이 |
|---|---|---|
| 1인칭 경험 서술 | "지난달 ○○학회 현장에서", "직접 출력해 보니" | selfhosted는 3인칭 정보성 — 그대로 쓰면 D.I.A.+ 경험 점수 없음 |
| 시간·장소·상황 디테일 | "행사 전날 밤 10시에 명단이 또 바뀌었다" 같은 구체 장면 | 기존 글은 일반론 장면("접수대가 혼잡하다") |
| 사진 중심 구성 | 본문 1,500자당 사진 3~5장, 각 사진에 한 줄 설명 | 기존 글은 브랜드 이미지 2장 고정 삽입 |
| 구어체 혼합 문체 | "~했어요/~하더라고요"와 "~합니다" 혼용, 짧은 감상 한 줄 | 기존 글은 보고서체 일관 |
| 모바일 문단 리듬 | 1~2문장마다 줄바꿈, 문단 사이 여백 | 기존 글은 3~4문장 문단 |
| 제목의 검색어 자연 포함 | 15~30자, 키워드 앞쪽, 낚시 없음 | 기존 SEO_NAVER_SYSTEM 규칙과 동일 — 재사용 |
| 본문 키워드 밀도 | 주 키워드 3~5회 자연 반복(기계적 반복 금지) | 신규 게이트 필요 |
| 단일 주제 블로그 | 명찰/학회/행사 축만 발행 (C-Rank) | 기획 08 정책 그대로 적용 |

### 1.2 피해야 할 신호 (게이트로 차단할 것)

- 마크다운 흔적(`##`, `**`, `|---|`)이 본문에 노출 — 붙여넣기 사고의 주범.
- AI 문어체 filler — 이번에 만든 `utils/text.py::filler_density` 게이트 그대로 적용. 단, 구어체("~했어요")는 filler가 아니므로 사전과 충돌 없음.
- 외부 링크 남발 — 본문 링크는 0~1개(맺음에 beoksolution.com 1회만). 네이버는 외부 유출 링크 많은 글을 눌러 내린다.
- 근거 없는 수치 — 기존 factcheck/`local_unsupported_claims` 게이트 그대로.
- 자체 블로그 글과의 본문 중복 — 같은 evidence로 selfhosted와 naver 원고를 만들면 유사문서 판정 위험. `similar_published()`(전 기간 검사, 이번에 확장한 것)를 채널 무관으로 적용.

### 1.3 "사람이 쓴 것처럼"의 실현 방법 — 2-pass 생성

1-pass(근거기반 섹션 생성)만으로는 보고서체가 남는다. **별도 humanize pass**를 둔다:

```
pass 1: 기존 엔진 — 근거팩 → 개요 → 섹션 (정보 골격, 사실 검증 가능 상태)
pass 2: NAVER_HUMANIZE 프롬프트 — 골격을 1인칭 현장 서술로 재작성
        - 입력: pass 1 본문 + 페르소나(행사 시스템 개발/운영 실무자) + 현장 장면 은행
        - 규칙: 사실·수치는 추가/변경 금지(재서술만), 사진 슬롯 마커 삽입,
                문단 리듬(1~2문장), 구어체 혼합 비율
pass 3: factcheck — pass 2 결과를 다시 근거팩과 대조 (humanize가 사실을 바꾸지 않았는지)
```

pass 2에서 사실이 왜곡되는 것이 최대 리스크이므로 pass 3 재검증이 필수다. 기존 `factcheck.check()`를 그대로 재호출하면 된다.

**페르소나 고정**: "비오케이솔루션에서 학회 등록·명찰 시스템을 만들고 행사 현장을 지원하는 실무자"로 고정한다. 매 글마다 페르소나가 흔들리면 블로그 전체의 일관성(C-Rank)이 깨진다. 허구의 구체 사례(가짜 학회명, 가짜 날짜)는 금지 — 장면은 "익명화된 일반 현장"으로만 쓴다("한 의학회 사무국에서" 수준까지 허용, "2026 대한○○학회에서"는 금지).

## 2. 복사-붙여넣기 최적화 — 출력물 설계 (핵심 기술 파트)

### 2.1 SmartEditor ONE 붙여넣기 특성 (설계 전제)

- **일반 텍스트 붙여넣기**: 서식 전부 소실. 마크다운 원문을 붙이면 `##` 문자가 그대로 노출 — 절대 금지.
- **rich text(HTML) 붙여넣기**: 브라우저에서 렌더된 페이지를 복사해 붙이면 굵게/목록/인용/표가 상당 부분 보존된다. 단 CSS 클래스·복잡한 중첩은 벗겨진다.
- **h2/h3 태그**: SmartEditor가 자체 "소제목" 포맷으로 항상 매핑해 주지는 않는다 → 소제목은 `<b>` + 크기보다는 **굵은 단독 문단**으로 넣고, 사용자가 에디터에서 소제목 스타일을 입히는 것을 체크리스트로 안내하는 편이 안전하다.
- **이미지**: 웹 이미지 URL을 포함해 붙여넣으면 외부 이미지 참조가 되거나 소실된다. **이미지는 붙여넣기 대상에서 제외**하고, 본문에 `[📷 사진 1: 이런 장면을 찍어 넣으세요 — 캡션 제안]` 형태의 슬롯 마커로 표시 → 사용자가 직접 촬영/보유 사진을 업로드. 직접 촬영 사진은 D.I.A.+ 가점 요소이기도 하다.

### 2.2 출력물: `paste.html` 1파일 (self-contained)

글 1건당 폴더 하나를 만든다: `out/naver/2026-07-06_학회-명찰-출력-준비/`

```
out/naver/2026-07-06_학회-명찰-출력-준비/
├── paste.html      ← 브라우저로 열어서 쓰는 작업 화면 (아래 상세)
└── draft.json      ← 원고 메타(제목/태그/키워드/검수 결과) — 재생성·추적용
```

`paste.html` 화면 구성 (외부 의존 없는 단일 파일, 로컬에서 브라우저로 염):

```
┌─────────────────────────────────────────────┐
│ [발행 체크리스트]                              │
│  제목(클릭=복사): 학회 명찰 출력, 사무국이 전날…   │
│  태그(클릭=복사): #학회명찰 #명찰출력 …(5~7개)     │
│  카테고리: 행사·학회 시스템   발행 권장 시간: 오전  │
│  사진 슬롯: 4곳 (본문에 📷 마커)                 │
├─────────────────────────────────────────────┤
│ [본문 전체 복사] ← 버튼 1개                     │
├─────────────────────────────────────────────┤
│ (렌더된 본문 미리보기 — 실제 복사되는 영역)        │
│  굵은 소제목 / 짧은 문단 / 인용구 / 표            │
│  📷 사진 1 슬롯: 노란 박스로 시각화 + 촬영 가이드   │
└─────────────────────────────────────────────┘
```

**복사 구현 방식** (신뢰도 순):

1. `[본문 전체 복사]` 버튼 → 본문 영역 노드를 `Range`로 선택 후 `document.execCommand('copy')`. 이 방식은 클립보드에 `text/html` flavor를 함께 싣기 때문에 SmartEditor에 붙일 때 서식이 보존된다. `file://`에서도 동작한다(구식 API지만 이 용도에는 가장 호환성이 좋다).
2. 폴백: `navigator.clipboard.write()` + `ClipboardItem({'text/html': ...})` — `file://`은 secure context라 대부분 동작하지만 브라우저별 편차가 있어 2순위.
3. 최후 수단: 버튼 없이 사용자가 미리보기 영역을 드래그 전체선택 → Ctrl+C. 화면에 이 안내 문구를 상시 표시.

**복사되는 HTML의 형태 규칙** (SmartEditor 보존율 최적화):
- 허용 태그: `<p>`, `<b>`/`<strong>`, `<blockquote>`, `<ul>/<ol>/<li>`, `<table>`(단순 2~3열), `<br>`.
- 금지: `<h1~h6>`(에디터 매핑 불안정 — 굵은 문단으로 대체), `<img>`(슬롯 마커로 대체), `style` 속성, `<div>` 중첩, 클래스.
- 사진 슬롯 마커는 복사본에는 `(📷 여기에 사진: ○○ 장면)` 텍스트 한 줄로 들어가고, 사용자가 그 줄을 지우고 사진을 업로드한다.

### 2.3 사용자 발행 워크플로 (하루 5분 목표)

```
1. paste.html 열기 (Windows 바탕화면 바로가기 or 폴더)
2. 제목 클릭 복사 → 네이버 에디터 제목에 붙여넣기
3. [본문 전체 복사] → 본문에 붙여넣기
4. 📷 마커 4곳 → 사진 업로드로 교체 (가이드 문구 참고)
5. 태그 클릭 복사 → 태그란에 붙여넣기
6. 소제목 3~4곳 에디터에서 "소제목" 스타일 적용 (체크리스트에 위치 표시)
7. 발행 → 발행 URL을 python run.py naver_mark <id> <url> 로 기록
```

## 3. 파이프라인 설계

### 3.1 상태 흐름 — 기존 상태머신에 "수기 종착" 추가

```
draft ─generate(naver_manual)→ draft(본문)
      ─factcheck→ ─review(naver 게이트)→ reviewed
      ─export→ awaiting_manual   ← 신규 상태: out/naver/에 paste.html 생성됨
      ─(사람이 발행 후 naver_mark)→ published (published_url 기록)
```

- 기존 `schedule/publish` 워커는 이 채널을 **절대 건드리지 않는다**: `channel='naver_manual'`을 새로 만들어 스케줄러/발행 워커의 대상 채널에서 제외. (기존 `naver` 채널과 분리 — 봇 경로와 섞이면 사고 위험.)
  - **구체 구현(검증 완료)**: 현 코드에서 `schedule_publish.run_once()`는 `reviewed`를 채널 무관으로 큐잉하고, `publish.py`는 `PUBLISHERS.get(channel)` 미등록 채널을 `failed` 처리한다. 즉 cron 겹침으로 naver_manual 글이 `reviewed`에 머무는 순간이 있으면 스케줄러가 주워가 failed로 오염시킬 수 있다. 방어 2중화: ① `generate_daily()`가 reviewed→export→awaiting_manual을 한 프로세스에서 원자적으로 진행, ② `schedule_publish._matches_focus()`에 `channel == 'naver_manual' → False` 가드 추가(1단계 범위에 포함).
- `awaiting_manual`은 DB 시야에서 "재고"가 아니라 "사람 대기함"이다. `status` 리포트에 별도 표기.

### 3.2 신규 명령 (run.py)

| 명령 | 동작 |
|---|---|
| `python run.py naver_draft` | 오늘자 원고 1건 생성 전체 흐름: 키워드 선정→근거→2-pass 생성→게이트→export. **당일 이미 awaiting_manual/published가 있으면 스킵**(하루 1건 강제). |
| `python run.py naver_mark <id> <url>` | 수기 발행 완료 기록. status→published, published_url 저장. 유사도 게이트의 비교 대상으로 편입됨. |
| `python run.py naver_queue` | 대기함 목록: awaiting_manual 건들과 paste.html 경로 출력. |

cron (Windows): `0 8 * * * python run.py naver_draft` — 매일 아침 8시 원고 준비, 사용자는 출근 후 발행.

### 3.3 키워드 전략 — 플랩패스 대응 클러스터

기획 08(주제 일관)을 따르되, 네이버 전용 키워드 뱅크를 분리한다(`tools/naver_keyword_bank.py`):

- **코어(플랩패스 직접 경쟁)**: 학회 명찰 출력 / 학회 명찰 제작 / 행사 명찰 출력 / 명찰 현장 출력 / QR 명찰
- **롱테일(경쟁 공백 — 우선 공략)**: 학회 접수대 준비물 / 명찰 재발행 대응 / 학회 사무국 체크리스트 / 참가자 명단 정리 / 현장등록 명찰 / 학술대회 등록 데스크 운영
- **연관 확장(2개월 차 이후)**: 학회 등록 시스템 / QR 체크인 / 학술대회 준비 일정

선정 로직: 네이버 검색 API(SERP 분석용 — `NaverSearchProvider`가 이미 구현돼 있음, **무료 키 발급만 필요**: developers.naver.com에서 Client ID/Secret)로 각 키워드의 상위 노출 블로그를 조회 → 최근 30일 내 우리가 안 쓴 키워드 중 경쟁 밀도가 낮은 것부터. 키가 없으면 뱅크 순서 라운드로빈으로 폴백(엔진은 키 없이도 동작해야 함 — Tavily 미사용 결정과 동일 원칙).

### 3.4 네이버 전용 게이트 (`tools/naver_quality.py`)

기존 게이트 재사용 + 신규:

| 검사 | 기준 | 출처 |
|---|---|---|
| grounding_ratio | ≥ 0.9 (pass 3 재검증 포함) | 기존 factcheck |
| filler_density | ≤ 0.6/1000자 | 이번에 만든 것 재사용 |
| HTML/마크다운 잔재 | `##`, `**`, `\|---\|`, `<div>` 등 0건 | markdown_guard 확장 |
| 전 기간 유사도 | 채널 무관 ≤ 0.55 (selfhosted 글 포함) | similar_published 재사용 |
| 제목 | 15~30자, 주 키워드 포함 | 신규 |
| 키워드 밀도 | 본문 주 키워드 3~5회 (6회 이상이면 차단 — 과최적화) | 신규 |
| 본문 길이 | 공백 제외 1,200~2,200자 (네이버 최적 구간) | 신규 |
| 사진 슬롯 | 3~5개, 각각 촬영 가이드 문구 포함 | 신규 |
| 문단 리듬 | 3문장 초과 문단 비율 ≤ 20% | 신규 |
| 외부 링크 | ≤ 1개 (beoksolution.com만 허용) | 신규 |
| 경험 서술 신호 | 1인칭 표지("직접", "현장에서", "해 보니" 등) ≥ 3회 | 신규 |
| 실명 리스크 | 실제 학회명/단체명 언급 0건 (허구 사례 방지) | 신규 |

게이트 탈락 시 humanize pass부터 재시도(최대 2회) → 그래도 실패면 그날은 스킵하고 다음날 다른 키워드로. **미달 원고를 억지로 내보내지 않는다** — 하루 1건이 목표지 의무가 아니다.

## 5. 운영 계획

- **주간 리듬**: 월~금 5건 (주말 발행은 네이버 체류지표가 낮아 비권장). 키워드 캘린더는 롱테일 3 : 코어 2 비율.
- **90일 목표**: 발행 60건+ 시점에 코어 키워드("학회 명찰 출력") 블로그 탭 1페이지 진입 여부 측정. 진입 실패 시 키워드 클러스터 재조정(더 좁은 롱테일로).
- **측정**: `naver_mark`로 기록된 URL을 주 1회 네이버 검색 API로 순위 조회(`tools/naver_rank_check.py` — 2단계 구현). 블로그 통계(조회/유입 키워드)는 사용자가 월 1회 수기 기록.
- **사진 준비**: 실행 전제 조건. 명찰 출력물/장비/현장 사진 풀(20~30장)을 미리 촬영해 두면 매일 슬롯 채우기가 5분 안에 끝난다. 없으면 이 기능의 D.I.A.+ 효과가 반감된다 — **구현과 병행할 사용자 숙제**.

## 6. 리스크와 완화

| 리스크 | 완화 |
|---|---|
| 유사문서 판정 (selfhosted 글과 근거 공유) | 채널 무관 전 기간 유사도 게이트 ≤0.55 + humanize pass가 문체를 완전히 바꿈. 그래도 같은 주제의 selfhosted 글과 **같은 주(week)에 겹치지 않게** 키워드 캘린더에서 오프셋 |
| humanize가 사실 왜곡 | pass 3 factcheck 재검증 (grounding <0.9면 재시도) |
| 허구 경험담 → 신뢰 리스크 | 실명/실제 행사명 금지 게이트 + 페르소나를 "시스템 개발·현장 지원 실무자"로 한정(실제 사업 범위와 일치) |
| SmartEditor 개편으로 붙여넣기 보존율 변화 | paste.html은 표준 태그만 사용, quality_selftest에 허용 태그 계약 고정. 개편 시 태그 규칙만 조정 |
| 발행 습관 끊김 (사람이 병목) | naver_queue로 대기함 가시화, 밀린 원고는 자동 폐기(3일 경과 시 archived — 오래된 원고를 늦게 올리면 시의성·중복 리스크) |

## 7. 구현 순서 (제안)

1. **1단계 (코어)**: prompts 2종 + `pipeline/naver_manual.py` + `render/naver_paste.py` + `naver_draft`/`naver_mark` 명령 + 기본 게이트(길이/키워드/슬롯/마크다운 잔재). → 첫 원고를 실제로 붙여넣어 보고 SmartEditor 보존율 실측.
2. **2단계 (게이트 완성)**: 문단 리듬/경험 신호/실명 게이트, selftest 회귀 추가, 키워드 사용 이력.
3. **3단계 (측정)**: 네이버 API 키 발급 후 SERP 기반 키워드 선정 + 주간 순위 추적.

1단계 구현 후 **실제 붙여넣기 테스트 1회가 최우선 검증**이다 — SmartEditor 보존율은 문서가 아니라 실측으로 확정한다.
